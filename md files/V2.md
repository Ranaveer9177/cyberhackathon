# VibeGuard — V2.md

# VibeGuard V2 — Secure Git Push

## Version

**Version:** v2.0  
**Feature:** Git Push Security Gate  
**Purpose:** Scan a project automatically before Git pushes to GitHub and block unsafe code from being pushed.

---

# 1. Main Objective

VibeGuard V2 integrates with Git so that when the developer runs:

```bash
git push
```

VibeGuard automatically runs before the push.

The workflow is:

```text
Developer
   ↓
git push
   ↓
Git Pre-Push Hook
   ↓
VibeGuard
   ↓
Security Scan
   ↓
Security Report
   ↓
Safe?
 ┌─┴──────────────┐
 YES              NO
  ↓                ↓
Allow Push       BLOCK Push
  ↓                ↓
GitHub           Developer fixes
```

VibeGuard becomes a security gate between the local repository and GitHub.

---

# 2. Core V2 Features

1. Git pre-push integration.
2. Automatic VibeGuard scan before push.
3. Scan the project before data leaves the local machine.
4. Detect secrets.
5. Detect vulnerable dependencies.
6. Detect source-code security issues.
7. Detect sensitive files.
8. Generate a security report.
9. Show security score.
10. Show CVE/advisory information where available.
11. BLOCK unsafe pushes.
12. Allow safe pushes.
13. Show the reason when a push is blocked.
14. Store VibeGuard configuration in the repository.
15. Install and remove the Git hook through VibeGuard.
16. Provide a controlled commit-and-push workflow.
17. Preserve normal Git behavior after the security check.

# 3. Important Git Workflow

## Normal Git workflow

A normal Git workflow is:

```text
Edit files
   ↓
git add
   ↓
git commit
   ↓
git push
```

The commit already exists before `git push` is executed.

Therefore, the Git `pre-push` hook should be responsible for:

```text
git push
   ↓
VibeGuard scan
   ↓
PASS / BLOCK
   ↓
Only PASS continues to GitHub
```

VibeGuard must not pretend that `git push` creates a commit.

# 5. Git Pre-Push Hook

VibeGuard installs a Git hook inside:

```text
.git/hooks/pre-push
```

The hook launches:

```text
vibeguard scan .
```

Example:

```bash
git push
```

Git executes:

```text
.git/hooks/pre-push
```

The hook executes:

```text
vibeguard scan .
```

VibeGuard returns an exit code.

```text
0 = SAFE
non-zero = BLOCK
```

# 7. What Causes a Push Block

The V2 security gate can block a push when configured blocking conditions are found.

Default blocking conditions:

```text
Critical vulnerability
Critical secret exposure
High-risk hardcoded credential
Known vulnerable dependency above blocking threshold
Private key detected
Unsafe security configuration above blocking threshold
```

Medium and Low findings can be reported without automatically blocking, depending on configuration.

Example configuration:

```text
Critical → BLOCK
High     → BLOCK
Medium   → WARN
Low      → WARN
Info     → REPORT
```

# 8. Dependency CVE Detection

The dependency scanner identifies the dependency and version.

Example:

```text
package.json

lodash: 4.17.20
```

VibeGuard sends the package information to its vulnerability intelligence source.

V2 MVP:

```text
Project
   ↓
Dependency Manifest
   ↓
Package + Version
   ↓
OSV API
   ↓
Vulnerability Record
   ↓
CVE / Advisory Alias
   ↓
Finding
```

Example finding:

```text
Package: lodash
Version: 4.17.20
CVE: CVE-XXXX-XXXXX
Severity: HIGH
Fixed Version: 4.17.21
```

VibeGuard must never create or guess a CVE ID.

# 12. Scan Scope

V2 should prioritize the code that is about to be pushed.

Preferred scan order:

```text
1. Changed files
2. Files staged/committed for the push
3. Dependency manifests
4. Required project configuration
```

A full-project scan remains available:

```bash
vibeguard scan .
```

The Git integration can use a changed-file scan for speed and a full dependency/security validation when required by configuration.

# 20. Bypass Protection

V2 should detect bypass attempts where practical.

The normal Git bypass option is:

```bash
git push --no-verify
```

This skips Git hooks.

VibeGuard cannot prevent Git itself from honoring Git's bypass mechanism.

Therefore V2 should document:

```text
Normal workflow:
git push
→ VibeGuard enforced

Bypass:
git push --no-verify
→ Git hook skipped
```

For stronger enforcement, V2 future versions should add remote-side CI enforcement so that a bypassed local hook cannot automatically become an accepted insecure change.

---

# 21. GitHub Protection — Future Extension

Local Git hooks protect the developer workstation.

For stronger protection:

```text
Developer
   ↓
Local VibeGuard
   ↓
GitHub
   ↓
GitHub Actions
   ↓
VibeGuard verification
   ↓
Merge allowed / blocked
```

This provides defense in depth.

The local hook improves developer feedback.

The remote CI check provides repository-level enforcement.

# 24. Exit Codes

VibeGuard must use predictable exit codes.

```text
0 = scan passed
1 = security policy blocked
2 = scanner/runtime error
3 = configuration error
4 = vulnerability intelligence unavailable
```

The Git pre-push hook uses the result to decide whether Git may continue.

---

# 25. Failure Handling

If the scanner crashes:

```text
VibeGuard scan failed.
Push blocked.

Reason:
Scanner unavailable.
```

For security-critical configurations, fail closed.

For example:

```text
Required vulnerability check unavailable
        ↓
BLOCK
```

Optional future configuration may allow specific checks to become warning-only.

# 29. V2 Security Principle

The core principle is:

> **Do not allow known security problems to leave the developer's machine through a normal Git push.**

VibeGuard is an independent verification layer.

It does not replace:

```text
developers
code review
testing
GitHub security tools
CI/CD
penetration testing
```

It adds a security gate before code is pushed.

---

# 30. V2 Limitations

1. A local Git hook can be bypassed with Git's hook bypass options.
2. A clean VibeGuard result does not prove that software is completely secure.
3. Vulnerability detection depends on available vulnerability intelligence.
4. Some vulnerabilities do not have CVE identifiers.
5. Static rules can produce false positives and false negatives.
6. Dependency version detection depends on supported package manifests.
7. Remote enforcement requires a separate CI/GitHub integration.
8. V2 does not automatically fix vulnerabilities.
